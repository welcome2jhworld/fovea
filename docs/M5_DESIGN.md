# M5 design: VLM re-check, semantic rules, follow-up questions

Scope: use a vision-language model where embeddings and detectors cannot
decide, without letting a model answer become a verified fact by default.

1. Re-check search candidates on the original footage and separate "not
   retrieved" from "retrieved but misread".
2. Rules with a VLM role (`describe` or `verify`) next to the M3 detector rule.
3. Natural-language rule drafting that shows the interpreted conditions and
   never activates on its own.
4. Follow-up questions over a search conversation through a small set of
   structured tools.

Every VLM output is an observation with evidence frame ids, a time range,
uncertainty and a status. The core validates evidence against the frames it
sent before anything is stored or shown.

## Models

| Role | Development Mac (M4, 16 GB) | Target (Windows x64, NVIDIA 24 GB) |

| Reference VLM (Transformers) | Qwen/Qwen3-VL-2B-Instruct, bf16 on MPS | Qwen/Qwen3.5-4B, bf16 on CUDA |

| Temporal grounding comparison | NemoStation/Marlin-2B-MLX-8bit | NemoStation/Marlin-2B (gated, needs approval) |
| Rule drafting and follow-up planning (text only) | the reference VLM in text mode | the reference VLM in text mode |

Qwen3.5-4B is not used on the development Mac: with Transformers 5.17 on MPS
its linear-attention layers fall back to reference kernels (130 s load and
112 s for a 16-frame clip, M0 smoke test), and the model was removed from this
machine to free disk. Qwen3-VL-2B-Instruct is the Mac stand-in for developing
and testing the contract; quality conclusions are only drawn per model, and the
target model is evaluated on the target machine.

An adapter (MLX, llama.cpp) is adopted for a role only after it matches the
reference on the same inputs: identical frame selection and timestamps, answers
agreeing on at least 90 % of the M5 evaluation items, and no evidence-contract
violations.

## Temporal grounding check

A backend may report precise event times only after it passes a calibration
run; otherwise its time ranges are ignored and results use the candidate range
that was sent.

- Calibration clips are generated by the worker (`fovea-worker calibrate-time`):
  a 12 s 640x360 clip with a burnt-in frame counter where a coloured square is
  visible from a known start to a known end (several placements: 1-3 s, 4-9 s,
  8-11 s), sampled at 2 fps.
- The backend is asked for the interval. Pass: start and end within 1.0 s on
  every placement, on both the frames-with-timestamps path and the video path
  (when the backend has one).
- The result is stored in the backend health as `temporal_grounding: verified |
  unverified` with the measured errors; the core reads it before trusting any
  time range from that backend.

## VLM job contract (worker)

`vlm_clip` (existing) is extended:

- Request: `frames[]` with `frame_id`, `pts_ns`, `utc_ms`, `index`, `path`;
  `clip {session_id, start_pts_ns, end_pts_ns, start_utc_ms, end_utc_ms}`;
  `gaps[]`; `task` (`verify_query`, `describe`, `verify_rule`, `order_events`);
  `question`; `language`; `limits {max_frames, max_pixels, max_new_tokens,
  deadline_ms}`; `generation`; `priority` (`realtime | search | background`).
- Response: `status` (`ok | unparsed | timeout | error | cancelled`),
  `verdict` (`match | no_match | uncertain`, for verification tasks),
  `observations[]` (text, evidence frame ids, start/end pts), `uncertainty`
  (`low | medium | high`), `raw_text` (bounded), model id and revision, input
  frames used, generated tokens, processing ms, peak memory when available.
- The prompt states the frame times explicitly and asks for JSON. Text that
  appears inside frames is data: the instruction says so, and the core never
  executes or follows model output.
- Missing JSON, unknown frame ids or ranges outside the clip make the answer
  `unparsed` or `uncertain`; they never become `match`.

## Scheduling and budgets (core)

- One VLM request at a time overall (`vlm` worker lane), separate from the
  `detect` and `embed` lanes.
- Priority queue with deadlines: `realtime` (rule verification) first, then
  `search` (user waiting), then `background`. A realtime task whose deadline has
  passed is dropped and recorded as `expired`, which makes the dependent rule
  observation `unknown`.
- Per-camera minimum share for realtime tasks: round robin across cameras with
  pending tasks; a camera never waits behind more than one task of another
  camera.
- Load estimate reported in `/v1/analysis`: `N x T / I` with N cameras having a
  VLM role, T the measured mean service time, I the request interval; plus
  deadline hit rate. `N x T / I < 1` is necessary but not sufficient; the hit
  rate is what the report states.
- Input limits per request: max frames, max pixels per frame, max new tokens,
  and the worker's peak memory is sampled and reported per model.

## 1. Search re-check

```
POST /v1/search {..., recheck: {enabled, max_candidates (default 5), budget_ms (default 60000)}}
  -> M4 ranges (top N)
  -> for the best max_candidates ranges: clip = range padded 2 s each side, clamped to the segment
     frames sampled at 2 fps (max 24), gaps listed
  -> vlm_clip task verify_query (priority search), sequential, stops at budget_ms
  -> each result: recheck {status, verdict, uncertainty, observations, evidence range validated, model, ms}
  -> results reordered: match first (by relevance), then uncertain, then no_match; unchecked keep relevance order
```

- The API reports `recheck_coverage` (checked / returned) and never labels an
  unchecked result as verified.
- Order-sensitive questions ("puts a box down and leaves" vs "walks up and picks
  a box up") use task `order_events`: the model must list the sub-events with
  times; the core accepts a match only when the sub-event order matches the
  question's order and each sub-event has evidence frames.
- Evaluation splits failures into `not_retrieved` (no candidate overlaps the
  ground truth) and `misread` (an overlapping candidate was checked and got
  `no_match`).

## 2. Rules with a VLM role

`vlm_role` on RuleRevision (already in the schema):

- `none`: M3 behaviour.
- `describe`: the event opens exactly as in M3. A background VLM task describes
  the evidence clip; its text is attached to the event as an observation.
  Failure is stored as a description error and does not change the event.
- `verify`: when the base condition reaches Active, the evaluator holds the
  trigger in `pending_verification` and a realtime task checks the clip against
  `verify_question` (for example "Is the person carrying a large box?").
  - `match` with valid evidence: the event opens; trigger latency includes the
    check and is reported separately.
  - `no_match`: no event; recorded as a rejected trigger (visible in the rule's
    activity, not as an alert).
  - `uncertain`, `unparsed`, `timeout`, `expired`, worker down: observation
    quality `unknown`; timers freeze per the evaluator contract; the next
    check is attempted after `recheck_interval_ms` while the base condition
    still holds. No event is opened on an unknown answer.
- Results carry rule revision and generation; a late answer for an older
  generation is ignored.
- Semantic rules are evaluated separately from detector rules in the
  verification report (trigger precision, rejected triggers, unknown ratio,
  added latency).

## 3. Natural-language rule drafting

`POST /v1/rules/draft {text, camera_id?, language}` returns a draft, never a
rule:

- The model fills a strict JSON schema of supported fields only: camera (from
  a provided list), zone (existing zone names or `needs_zone`), schedule days
  and times, time zone, target class (`person` in this build), minimum dwell
  seconds, max observation gap, severity, actions, `vlm_role` and
  `verify_question`.
- A deterministic validator checks every field. The response lists:
  `interpreted` (field, value, the text span it came from), `unsupported`
  (phrases that map to no supported condition, for example counting people,
  vehicle classes, loitering across cameras), `ambiguous` (phrases without a
  decidable criterion, for example "suspicious behaviour", "acting strangely";
  these are never converted into a verify question automatically), and
  `missing` (required fields the text did not give).
- The console shows the draft as a structured form with those four lists; the
  operator edits and saves through the normal rule API, and a saved rule starts
  disabled until the operator enables it.
- Evaluation set `eval/rules/drafts.json`: Korean and English rule texts with
  the expected structured result, including unsupported and ambiguous cases;
  metrics are exact-field accuracy, unsupported/ambiguous detection rate, and
  the number of drafts that would have produced a wrong enabled rule (must be
  zero because drafts are never enabled).

## 4. Follow-up questions

A search conversation keeps state in `search_sessions`: time range, cameras,
active conditions, result ids, selected result, last question.

`POST /v1/search/{session_id}/follow-up {text}`:

- The planner (reference VLM, text mode) must answer with one tool call from
  a fixed list; anything else is rejected:
  - `refine {keep_result_ids | from_results: all, condition_text}` runs a VLM
    `verify_query` over the listed results only.
  - `search {query, time_range?, camera_ids?}` runs a new search inside the
    conversation's time and camera scope unless the user widened it explicitly.
  - `filter_time {from, to}`, `filter_cameras {camera_ids}`.
  - `select {result_id}`.
- Arguments are validated against the session (ids must exist, times inside
  retained footage, cameras exist). Maximum 3 tool calls per follow-up, 10 VLM
  checks per follow-up, and the search budget above.
- No SQL, shell, file paths or free-form code reach the core; the planner sees
  only ids, times and camera names. Text read from frames or earlier model
  output is passed as quoted data, never as instructions.
- "그중 두 사람이 있던 장면" becomes `refine {from_results: all,
  condition_text: "two people are visible"}` and returns the subset with
  verdicts and evidence.

## Console

- Search: re-check toggle, per-result verdict chip (verified match, no match,
  uncertain, not checked) with the model name, evidence frames highlighted on
  the player timeline, follow-up input under the results with the tool call
  that ran shown in one line.
- Rules: `vlm_role` selector, verify question field, rejected triggers in the
  rule activity; natural-language draft panel ("Describe the rule") that fills
  the editor and shows interpreted, unsupported, ambiguous and missing items.
- Alert detail: VLM description and verification result with evidence.

## Verification (scripts/verify_m5.py, eval)

- Temporal calibration result per backend recorded.
- Search re-check on `eval/search/questions.json`: precision@5 before and after
  re-check, negatives answered `no_match`, misread vs not-retrieved counts,
  re-check latency and budget stops.
- Order-sensitive pair from a generated or recorded clip: both orders
  distinguished or reported as uncertain, never both matched.
- Semantic rule on the classroom clip with a verify question that is true and
  one that is false: one event for the true question, rejected triggers for the
  false one, unknown during a forced worker outage.
- Draft evaluation on `eval/rules/drafts.json`.
- Follow-up: a two-turn conversation on the corpus produces the expected tool
  calls and a result subset whose evidence validates.
