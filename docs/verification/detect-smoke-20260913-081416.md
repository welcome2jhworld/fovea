## Finding fixed during the run: ids dropped while the tracker still matched

First run (before the fix) gave track id 1 on f0000-f0001 only and null on f0002-f0006 even though RF-DETR found the
car with 0.75-0.83 confidence. Raw per-frame ByteTrack trace (pixel boxes, `post-tracks` = tracked tracks after the
update with (external id, tlbr, score), `out ids` = what `update_with_detections` returned):

Frames 3-5: the tracker matched the car (track 1 updated, score equals the detection score) but supervision's
`update_with_detections` re-associates the output by IoU >= 0.5 between the Kalman posterior box and the detection; the
Kalman filter is tuned for 30 fps and smears the box at 2 fps (IoU 0.42-0.49), so the id was discarded. The adapter now
calls `update_with_tensors` and maps tracks back to input rows by exact score equality (IoU tie-break), falling back
to IoU gated at the tracker's own matching threshold. First-run raw summary for the record:

## Known gaps

- Track ids fragment when an object leaves through the frame edge at 2 fps with the default 0.8 match threshold
  (see above); FOVEA_TRACK_MATCH_THRESHOLD=0.9 keeps the id on this clip but is untested on crowded scenes.
- supervision 0.30.2 marks ByteTrack deprecated (removal in 0.31.0, replacement is the `trackers` package); the adapter
  isolates that dependency to one class.
- Only the nano variant was exercised; `FOVEA_DETECTOR_MODEL=small` is wired but its checkpoint was not downloaded.
- No CUDA machine available; the cuda branch of device selection is untested. The MPS to CPU fallback path is
  implemented but was not triggered (MPS inference succeeded on every frame).
