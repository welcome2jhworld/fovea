# Detection lane over HTTP, single-frame jobs 2026-09-13T11:04:39Z

M3 worker check: one-frame `detect_frames` jobs sent to `fovea-worker serve` the
way the core's AnalysisScheduler sends them (one request in flight, round robin
over cameras), with tracking continuity across jobs, warmup, health turnaround
and clean stop. Earlier multi-frame results are in `detect-smoke-20260913-081416.md`.

Machine: Apple M4 (10 cores), 16 GB, macOS 26.3 arm64. Worker venv: Python 3.12.8,
torch 2.14.0 (MPS available), rfdetr 1.10.1, supervision 0.30.2, RF-DETR Nano
weights already cached. The machine was shared with other work during every
run (another lane's fovea-core with four rtsp-testsrc streams, builds, a desktop
app); the 1-minute load average is printed with each run.

## Command

From the repo root:

```
PYTHONPATH=worker worker/.venv/bin/python -m fovea_worker.cli bench-serve <frames> \
  --jobs N --cameras C --fps 2 --pace realtime|max --stop signal|stdin [--budget-p95-ms 100]
```

`bench-serve` starts `serve --backend dry --detector rfdetr --port 0 --token-file
--info-file --warmup --exit-on-stdin-eof` as a child, waits for the info file and
for `detector_state == ready`, then sends one job at a time, each carrying one
frame (pts = frame index x 0.5 s per camera, frames loop when jobs exceed frames,
pts keeps increasing). Round trip is measured by the client around the HTTP
request; worker per-frame time comes from `per_frame_ms` (image decode, predict,
tracker update); health turnaround is the worker's `detector_turnaround_ms`
(last 200 jobs). At the end the child is stopped with SIGTERM (`signal`) or by
closing its stdin (`stdin`) and its exit code is recorded.

| lot | one 108-frame job, box padding off | id 1: 10; None: 36 | ids 2, 4, 3: 8, 6, 3; None: 5 |

No run logged a tracker reset or rate change: every camera's only note was
`created`. The code before this change (HEAD, eager model, old registry) and
this change with padding off gave identical per-frame person ids and confidences
on the 108 lot frames, so the registry rework and the traced model do not
change tracking; the id differences in the table come from the box padding
(`FOVEA_TRACK_BOX_BUFFER`, default 0.3), which keeps the fourth seated person
on one id for the whole clip.

The lot person detections without an id (frames 50-58 and 92-98 of 108) are a
person about 0.036 frame widths wide walking along the top edge, moving 0.035 to
0.057 frame widths per 0.5 s: consecutive boxes do not overlap even with
padding, so ByteTrack's IoU association cannot link them at 2 fps.

## Findings during the run

1. Worker aborted at exit. The first run (eager model) ended with exit code -6
   and `Fatal Python error: _enter_buffered_busy: could not acquire lock for
   <_io.BufferedReader name='<stdin>'> at interpreter shutdown, possibly due to
   daemon threads`: the `--exit-on-stdin-eof` watcher blocked inside
   `sys.stdin.buffer.read` while SIGTERM stopped the worker. It now reads the raw
   descriptor. `test_stop_signal_exits_cleanly_while_stdin_is_still_watched`
   failed 3 of 3 times against the old reader and passes 3 of 3 with the fix.
   That run's latency: round trip p50 73.5 / p95 95.9 / max 112.0 ms, worker per
   frame p50 71 / p95 94 ms.

2. 960x540 inference was slower than the 40 ms measured at 640x360, and
   sensitive to CPU load. In-process profile, 40 classroom frames with 0.45 s
   idle between frames (load average rose from 5.9 to 15 during these four runs):

   | Variant | p50 / p95 / max ms | Detections vs eager |
   | --- | --- | --- |
   | eager (before) | 76.9 / 215.9 / 275.9 | - |
   | `inference(compile=False)` float32 | 98.4 / 165.1 / 484.7 | identical |
   | `inference(compile=True)` float32 (torch.jit trace) | 64.0 / 80.0 / 81.6 | identical (697 boxes, 0 px and 0.000 score difference at 0.1 px / 0.001 rounding) |
   | `inference(compile=False)` float16 | 91.6 / 176.4 / 317.7 | different in 13 of 40 frames, box difference up to 322.7 px |

   The detector now builds the traced float32 model (`FOVEA_DETECTOR_TRACE=0`
   keeps eager). Traced predict time against the idle gap before each frame,
   each call on a new thread like the HTTP server, 40 frames per gap:
   0 ms 42.5 / 52.5, 50 ms 37.7 / 42.0, 125 ms 52.8 / 56.7, 250 ms 59.4 / 61.5,
   500 ms 59.5 / 61.1 (p50 / p95 ms). A frame after an idle gap costs about
   15-20 ms more. Running predict on a new thread per call made no difference
   in an earlier eager comparison (back to back: main thread 59.3 / 69.8, new
   thread 55.3 / 65.7; with 0.45 s gaps: 75.1 / 95.8 and 69.6 / 85.3).

3. The 100 ms p95 budget is not guaranteed under contention. Every
   traced 960x540 bench-serve run, in order:

   | Run | Round trip p50 / p95 / max ms | Load avg |
   | --- | --- | --- |
   | 1 camera realtime, 66 jobs | 65.1 / 78.8 / 91.8 | 7.40 |
   | 4 cameras realtime, 264 jobs | 57.8 / 132.8 / 147.4 (over budget) | 6.62 |
   | 1 camera back to back, 200 jobs | 51.2 / 55.9 / 60.8 | 6.50 |
   | 4 cameras realtime, 120 jobs | 41.0 / 62.0 / 76.0 | not recorded |
   | 4 cameras realtime, 264 jobs | 42.2 / 64.0 / 81.5 | 6.25 |
   | final A, B, C, A2 | see the table above | 4.9-6.2 |

   In the over-budget run the worker's own per-frame time had the same tail
   (p50 56, p95 130 ms), so the time went to the detector, not to HTTP. Another
   lane's fovea-core with four rtsp-testsrc processes started within the same
   minute; that it caused the tail is likely but not proven.

## Known gaps

- Windows was not run: `scripts/windows/setup-worker.ps1`, the CTRL_BREAK stop
  path and the Windows clock test are untested (no Windows machine or
  PowerShell here; the CI worker job runs on Ubuntu).
- No CUDA machine: the traced model on CUDA and the cu128 wheel install are untested.
- The latency budget held in 8 of 9 traced 960x540 runs; heavy GPU or CPU work
  from other processes can push p95 past 100 ms (finding 3).
- At 2 fps a small object that moves more than its own width per frame gets no
  track id (lot clip, frames 50-58 and 92-98).
- supervision 0.30.2 still marks ByteTrack deprecated (removal in 0.31.0).
